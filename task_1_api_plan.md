## Module layout

All JavaScript lives in `src/` as native ES modules. Each page loads exactly one external module
entry (`<script type="module" src="src/pages/<page>.js">`) and nothing else: no classic scripts
(the mobile-menu styles use the CSS media query `@media (scripting: enabled)` instead of a
"js" class set by a script). There are no inline scripts, no `window.*` globals and no
`js/` folder any more: the Phase 1 scripts were converted to modules on 2026-11-12. Modules need
http, so open the site with `npm run start` (or `npm run dev`), not by double-clicking the file.

### 1. Folders and what each one owns

| Folder            | Owns                                                                                                                                                                                                  | May import                 | Must not                                     |
| :---------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------- | :------------------------------------------- |
| `src/utils/`      | Pure helpers: money in cents, cart math, query strings, validation, storage wrapper, DOM helper                                                                                                       | nothing from the app       | call `fetch`; read app state                 |
| `src/api/`        | Talking to the REST API: one fetch wrapper (`http.js`), one file per resource, `ApiError`                                                                                                             | `utils/`                   | touch the DOM or state; store anything       |
| `src/state/`      | What the app remembers: cart, saved items, session, catalog filters; persistence through `utils/storage.js`                                                                                           | `utils/`                   | call the API (results are passed in)         |
| `src/components/` | Rendering and user events for one piece of UI. Live Phase 1 features export `init()` (they enhance markup already in the page); planned API components export `mount(root, deps)` returning `unmount` | `api/`, `state/`, `utils/` | import `main.js` or reach outside its `root` |

Dependency direction: `pages -> main.js, components -> (api, state) -> utils`. Nothing points upward.

### 4. Key flows

- **Browse:** `filter-bar` -> `state/catalog.update()` -> URL changes -> `main.js` calls
  `api/products.listProducts(query)` -> `product-list` and `pagination` render `data` and `meta`.
- **Sign in:** `login-form` -> `utils/validate` -> `api/auth.login` -> `state/session.signIn` ->
  redirect to the `returnTo` flag (sessionStorage) or the account page.
- **Any 401:** `api/http.js` calls `onUnauthorized` -> `state/session.signOut()` -> login form
  with a "session expired" message. Cart and saved items are kept.
- **429:** `ApiError.retryAfter` -> `status-message` shows "Try again in N s"; buttons for that
  action are disabled until then. No automatic retry (avoids making the limit worse).
- **Cancel order:** shown only when `cancellable` is true; a 400 `ORDER_NOT_CANCELLABLE` refreshes
  the list (status changed on the server).

### 5. Money and ids

All prices are integer cents end to end (API and client); formatting happens only in
`utils/money.formatMoney`. Product ids are slugs; address ids are chosen by the client (slug of
the label plus a short random suffix), which makes `PUT /account/addresses/{id}` safe to retry.

## Storage strategy

Rule of thumb: decide by what must survive **refresh**, **tab close** and **logout**.
`localStorage` survives all three; `sessionStorage` survives refresh only (it is per tab and is
cleared when the tab closes); memory survives nothing; the URL survives refresh and can be shared.

| Data                                                                                                                                           | Where            | Key                     | Refresh   | Tab close                      | Logout      | Why                                                                                                                                                                                                 |
| :--------------------------------------------------------------------------------------------------------------------------------------------- | :--------------- | :---------------------- | :-------- | :----------------------------- | :---------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cart lines (`productId`, `quantity`, price snapshot)                                                                                           | localStorage     | `brandstore:cart:v1`    | kept      | kept                           | kept        | A shopper expects the cart tomorrow and after signing out/in. It holds no personal data. Prices are re-checked against `GET /products/{id}` before checkout, so a stale snapshot cannot be charged. |
| Save-for-later items                                                                                                                           | localStorage     | `brandstore:saved:v1`   | kept      | kept                           | kept        | A wishlist is only useful if it lasts; same content and risk level as the cart.                                                                                                                     |
| Session: token, `expiresAt`, user `{id, name, email}`                                                                                          | sessionStorage   | `brandstore:session:v1` | kept      | **cleared**                    | **cleared** | Refresh must not sign the user out, but a bearer token should not outlive the tab (shared computers). Cleared on logout and on any 401.                                                             |
| Transient flags: `returnTo` after login, "session expired" notice, dismissed rate-limit banner, last cancelled order id for a one-time message | sessionStorage   | `brandstore:flags:v1`   | kept      | cleared                        | **cleared** | Only meaningful during this visit; must not leak into a later visit or another user's session.                                                                                                      |
| Catalog filters, sort, page                                                                                                                    | URL query string | n/a                     | kept      | n/a (in history and bookmarks) | unaffected  | Shareable and back/forward work; storing them would make the URL lie.                                                                                                                               |
| Products, orders, addresses from the API                                                                                                       | memory only      | n/a                     | refetched | gone                           | cleared     | The server is the source of truth. Orders and addresses are personal data and are never written to the device.                                                                                      |

### Decisions and trade-offs

1. **Why not localStorage for the token?** It would survive closing the browser, so the next person
   on a shared computer would be signed in. sessionStorage limits that to the open tab.
2. **XSS.** Any script on the page can read both storages. Mitigations already in place: the
   Content-Security-Policy from Phase 1 (`script-src 'self'`) and rendering with `textContent`
   only. The safer design is an HttpOnly cookie set by the server; the contract returns the token
   in the body, so that is listed as a backend follow-up, not something the client can do.
3. **Keeping the cart after logout** is a product choice (it matches most stores and avoids
   losing a guest cart at sign-in). If the business wants per-user carts, logout also clears
   `brandstore:cart:v1` and the cart moves to a future `/account/cart` endpoint.
4. **Versioned keys** (`:v1`): if the stored shape changes, the key changes and old data is ignored
   instead of crashing the app.
5. **Failure handling:** `utils/storage.js` wraps every call in try/catch (private mode, disabled
   storage, `QuotaExceededError`) and returns the fallback; the app keeps working in memory.
6. **Token expiry:** `expiresAt = now + expiresIn * 1000` is stored with the token; the session is
   treated as signed out once it passes, without waiting for a 401.

### What logout does

`state/session.signOut()` removes `brandstore:session:v1` and `brandstore:flags:v1`, drops orders and
addresses from memory, and leaves `brandstore:cart:v1` and `brandstore:saved:v1` untouched.

### 3. Cases for the three high-risk areas

**Cart math (unit)**

- `lineTotal` = unitPrice x quantity in cents; no floats (e.g. 3 x 1999 = 5997, not 59.97 x 100).
- `subtotal` of [] is 0; sums many lines exactly (100 lines of 1999).
- `shippingFor(9999)` = 799, `shippingFor(10000)` = 0 (threshold is inclusive, same rule as the API).
- `clampQuantity`: 0, -1, NaN, 1.5, "3" -> 1, 1, 1, 1, 3; never above `min(stock, 10)`; stock 0 -> line removed by the cart.
- `totals` matches the API order totals for the seeded orders (o-1001..o-1003) exactly.
- Cart store: adding an existing product increments quantity; a corrupt `brandstore:cart:v1` value is ignored, not thrown.

**Auth**

- Unit: `createSession` with an injected clock: signed in until `expiresAt`, signed out after; `signOut` removes session and flags but keeps cart and saved keys.
- Integration (MSW): requests to `/account/*` carry `Authorization: Bearer <token>`; a 401 calls `onUnauthorized` exactly once and clears the session; login 400 maps `details` to field errors; 401 shows "Email or password is incorrect"; 429 `TOO_MANY_LOGIN_ATTEMPTS` shows the Retry-After seconds and disables the button.
- E2E: sign in with the demo account, refresh (still signed in), open the orders page, sign out (account pages redirect to login; cart still there).

**Query-string building**

- Unit: `buildQuery({ category: 'electronics', q: '', page: 1 })` -> `?category=electronics&page=1` (empty dropped, keys sorted); spaces, `&`, `#` and non-ASCII are encoded; `parseCatalogQuery('?limit=500&sort=cheapest')` falls back to defaults (never sends a request the API would 400); round trip `parse(build(x))` equals `x`.
- Integration: changing the category resets `page` to 1; MSW asserts the exact URL; a 400 response renders its `details`.
- E2E: filter + page 2 + Back restores the previous results; opening a copied URL shows the same results.
