Complication

Black Friday is the worst week to discover how a front end breaks

  • Traffic peaks on the routes campaigns link to: the catalog and product pages.
  • Mobile networks are slower under load; the same build behaves differently on 3G.
  • Every change is risk in the freeze window, including migration work that is otherwise safe.
  • We have no real-user data yet: the shop has run only against the TechSphere API kit and our own scripted sessions.

So the question is not only "is it built?"

It is: is it measured, guarded by CI, observable in production, and is the unfinished part clearly separated from what we ship?

What shipped

Routes, a component system, checkout and the dashboard

Routes

13 working routes: home, catalog, product, cart, 3 checkout steps and confirmation, sign-in, register, order history, admin, 404. Account, checkout and admin are protected, with a return path after sign-in.

Component system

17 typed shared components (Button, Input, Select, Modal with focus trap, DataTable with sorting and paging, Tabs, Steps…), 11 in Storybook, axe on every story, brand colours only.

Checkout

One pure cart reducer in integer cents; 3 validated steps; the draft survives refresh and Back; exactly one order however fast the clicks; a clear error and a safe retry when the API fails.

Admin dashboard

Sales, orders, average order value, sales by category and by month, each chart with its table. Admin only, in a separate download shoppers never receive.

Not a complete migration: the legacy pages are still live. Addresses and compare are served by them until wave 5.

Top risks

  • 3G shoppers wait 4.5 s on the catalog. Mitigation: start the catalog request with the JavaScript; cache it at the CDN.
  • API under peak load never tested beyond the kit. Mitigation: load test; checkout already retries safely.
  • No real-user baseline. Mitigation: watch-only for 2 weeks, then set alert thresholds.
  • Session readable by injected script. Mitigation: no raw HTML, one-hour tokens; cookies in wave 6.

Pages that wait for the API before their first content pay twice: 125 KB of JavaScript, then the API round trip. Cart and sign-in render without an API call. Fix: start the first catalog request in parallel with the JavaScript and cache it at the CDN; the CI budget keeps it from regressing.

Monitoring plan

Realistic without analytics data: hooks now, counting with the backend

Error tracking

live

Uncaught errors, unhandled rejections and route errors captured; sent once the endpoint is set.

Scheduled Lighthouse

live

Daily and after each deploy on production, same budgets as PRs; a miss opens an issue.

Web Vitals

live

LCP, INP and CLS from every page view with the web-vitals library, through the same sink.

Funnel events

3 of 7 wired

Product → cart → checkout steps → purchase. Counting needs the backend's events endpoint.

Response process

Accessibility regression in CI: the merge is blocked; fix in the same PR, add a test. Drop in checkout completion: check errors, then the API, then the last deploy; roll back first if a deploy is in the window. Thresholds are starting points until two weeks of real traffic set the baseline.

Recommendations

Protect, invest, investigate, defer

Protect

The CI gates (coverage floors, end-to-end checkout, axe, Lighthouse budgets), the cart reducer and its tests, the idempotent checkout. They stopped PR #17 and make a release safe in the freeze.

Invest

The production API, the monitoring endpoint and a checkout load test; the 3G fix for the catalog. These are the only open items between v2.0.0 and Black Friday.

Investigate

Real-user Web Vitals after launch: how many shoppers are on slow networks? Server-side rendering for the catalog only if real LCP misses target. Which error-tracking vendor.

Defer

Addresses and compare pages, cutover, cookie sessions, Arabic, visual regression tests. None sells more on Black Friday; each adds risk in the freeze.
